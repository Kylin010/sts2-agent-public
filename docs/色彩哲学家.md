# 色彩哲学家（COLORFUL_PHILOSOPHERS）研究 · 铁甲战士 A10 · v0.111.0

> 2026-10-03。来源：反编译源码（`decompiled/v0.111.0/`，只做个人研究）、spire-codex 事件/卡牌数据、社区对局（`ironclad-a10-v0.111.0.jsonl.gz` 9761 局；样本不够时补充全版本 `ironclad-a10-all.jsonl.gz` 70395 局，单独标注）。
> 标注：【源码】= 读代码确认；【统计】= 社区数据，有选择偏差，只说明「相关」；【判断】= 我按机制推出来的，没有直接数据。

## 0. 结论速览

1. **机制【源码】**：只在**第二幕（巢穴）**出现。铁甲能看到「粉 / 橙 / 绿 / 蓝」四种颜色里随机 3 种（红色永远不给自己）。选一种颜色后**不是直接给 3 张牌**，而是弹出 **3 次「3 选 1」**：一组**全普通**、一组**全罕见**、一组**全稀有**（稀有那组**保证是 3 张稀有**，不受 A10「稀有率减半」影响）。每组都能跳过，没有任何代价（不扣血、不扣钱、不塞诅咒）。
2. **频率【统计】**：活着进第二幕的局里约 **9%** 会碰到（526 / 5851）；按全部对局算约 5.4%。我们的程序约 60~65% 的局能进第二幕 → **约每 18 局碰到 1 次，200 局约 11 次**。
3. **选哪个颜色**：默认 **蓝（故障机器人）≥ 绿（静默猎手）> 橙（储君）> 粉（亡灵契约师）**；牌组已有消耗引擎时**橙色排第一**（暴政、轰击、护驾、冲锋都直接吃消耗）。颜色的差别比「拿什么、拿几张」小得多。
4. **拿什么**：每个颜色 80 张牌里，对铁甲 S/A 档（该拿）只有 5~9 张、B 档（缺才拿）18~21 张，其余 51~55 张要么依赖本角色机制（充能球、星辉、奥斯提、中毒、奇巧、灾厄）几乎没用，要么只是平庸的过渡牌。**稀有组：S/A 档一定拿；罕见组：A 档拿、B 档缺这类才拿；普通组：只拿 A 档**。一般拿 1~2 张，不要三张全拿。
5. **我们程序三次全跳过的原因**（第 6 节）：① 选牌模型不认识这些牌（这个事件一个地图点有 9 张候选，训练脚本只收 2~5 张的地图点，**整个事件被训练数据丢掉了**），9 张里 6 张按「未知牌」固定给 −0.5；② 知识库只收铁甲/无色牌，**战斗规划器看不懂别家牌**（抽牌、能量、易伤都不认识）；③ 选牌时的模拟实打（simeval，2 个样本）**噪声远大于牌的价值**：多一张从来没被打出的牌，实打结果就能差 40 血。没有实打这一项，程序本来会拿光束射线等牌；跳过是实打这一项定的。
6. **值不值得写规则**：值得，但只做小规则（一张分档表 + 事件选色 + 选牌直接查表，约 50 行），优先级中低。这张表还能复用到先古遗物**万花筒**（拿到时 2 次别家卡牌奖励）和**棱彩宝石**（之后所有卡牌奖励混入别家牌）。更值得修的是第 6 节暴露出的**实打噪声**——它影响所有选牌，不只是这个事件。

## 1. 精确机制【源码】

### 1.1 什么时候出现

- **只属于第二幕「巢穴」**：`MegaCrit.Sts2.Core.Models.Acts/Hive.cs:31-43` 的 `AllEvents` 里有 `ColorfulPhilosophers`，第一幕、第三幕的事件表里没有，共享事件表（`ModelDb.cs:157`）里也没有。社区 526 次全部在第二幕【统计】。
- **出现条件**：`ColorfulPhilosophers.cs:29-32`

  ```csharp
  public override bool IsAllowed(IRunState runState)
  {
      return runState.Players.All((Player p) => p.UnlockState.CharacterCardPools.Count() > 1);
  }
  ```
  只要求解锁了不止一个角色的卡池。另外它在纪元锁 `Event3Epoch`（`Timeline.Epochs/Event3Epoch.cs:33`）里，没揭开纪元的存档不会出；sts2-cli 全解锁，恒满足。和血量、金币、楼层都无关。
- **怎么被抽到**：`ActModel.cs:331-347` 把本幕 10 个事件 + 18 个共享事件洗成一个队列；每进一个问号事件房，`RoomSet.cs:110-124` 从队列往后找第一个「此刻允许且本局没见过」的事件。所以每个事件机会大致均等，**一局最多一次**。

### 1.2 给哪几个颜色

`ColorfulPhilosophers.cs:18-25, 34-52`

```csharp
CardPoolColorOrder = { Necrobinder, Ironclad, Regent, Silent, Defect };   // 粉、红、橙、绿、蓝
foreach (CardPoolModel cardPool in CardPoolColorOrder)
    if (character.CardPool != cardPool && list2.Contains(cardPool))      // 去掉自己的颜色、去掉没解锁的
        list.Add(new EventOption(... OfferRewards(cardPool) ...));
int num = Mathf.Min(3, list.Count);
while (list.Count > num)
    list.RemoveAt(base.Rng.NextInt(list.Count));                         // 随机删到只剩 3 个
```

- 铁甲**永远看不到红色**；四个候选（粉、橙、绿、蓝）随机删一个，剩下 3 个按「粉、橙、绿、蓝」的顺序排列。每个颜色出现的概率都是 3/4。
- 事件文本里列了 5 个选项（`events.json`），那只是本地化表，实际只会给 3 个。

### 1.3 选了颜色之后：三次「3 选 1」

`ColorfulPhilosophers.cs:54-66`

```csharp
options  = new CardCreationOptions([pool], CardCreationSource.Other, CardRarityOddsType.Uniform, c => c.Rarity == CardRarity.Common)
               .WithFlags(NoRarityModification | NoCardPoolModifications);
options2 = ... c => c.Rarity == CardRarity.Uncommon ...
options3 = ... c => c.Rarity == CardRarity.Rare ...
await RewardsCmd.OfferCustom(base.Owner, new List<Reward>(3) {
    new CardReward(options,  3, base.Owner),     // 3 = DynamicVars.Cards
    new CardReward(options2, 3, base.Owner),
    new CardReward(options3, 3, base.Owner) });
```

逐条解释：

| 问题 | 答案 | 出处 |
|---|---|---|
| 直接给还是选？ | **三个独立的卡牌奖励**，每个 3 张里选 1 张；最多拿 3 张 | 上面的代码；社区数据里这个地图点固定 9 张候选、最多 3 张被选【统计】 |
| 稀有度？ | 第一组全普通、第二组全罕见、第三组全稀有。`Uniform` 不掷稀有度，只按过滤条件取 → **稀有组一定是 3 张稀有**，A10 的「稀有率减半」管不到这里 | `CardFactory.cs:214-242`（`RarityOdds == Uniform` 时直接用过滤后的列表） |
| 同组会重复吗？ | 不会：同一个奖励里已经出过的牌进黑名单 | `CardFactory.cs:89-97`（`list` 作为 blacklist） |
| 从多少张里抽？ | 单人局每个角色 **普通 20 / 罕见 35 / 稀有 25**（「仅多人模式」的牌被过滤：每色 3 张罕见 + 2 张稀有） | `CardFactory.cs:25-32` `FilterForPlayerCount`；张数按 `cards.json` 统计 |
| 会不会带升级？ | 普通 / 罕见各有 **12.5%** 带升级（A10，第二幕：幕序号 1 × 0.125），稀有 0% | `CardFactory.cs:23, 288-305`；社区实测普通 15.3%、罕见 16.1%、稀有 3.3%（多出来的部分来自会提高升级率、或加牌时自动升级的遗物）【统计】 |
| 能跳过吗？ | 能，每组单独跳过（`CanSkip` 默认 true），跳过没有任何惩罚 | `Rewards/CardReward.cs:95, 312-319` |
| 代价？ | **没有**。不扣血、不扣金币、不加诅咒，唯一的成本是占了一个问号房 | 整个事件只有 `OfferRewards` 一个动作 |
| 棱彩宝石会混色吗？ | 不会：带了 `NoCardPoolModifications` | `Relics/PrismaticGem.cs`（检查这个标记后直接返回） |

| 口径 | 数值 |

| 进入第二幕的局（v0.111.0） | 5851 |
| 其中碰到色彩哲学家 | 526（**9.0%**）；全版本 2872 / 33566 = 8.6% |

理论值对得上：第二幕候选约 26 个（28 个减去第一幕用掉的共享事件），每局约 3 个事件房 → 3/26 ≈ 11%，再扣掉中途死掉的局 ≈ 9%。

### 3.1 选哪个颜色、胜率

## 4. 铁甲战士该选哪个颜色

### 4.1 按「三组里能拿到多好的牌」算期望【判断 + 计算】

按第 5 节的分档（S=3、A=2、B=1、C/X=0，每组 3 张里取最好的，都不值得就跳过 = 0），从各自卡池随机抽 3 张算期望：

| 颜色 | 普通组期望 | 罕见组期望 | 稀有组期望 | 合计 | 稀有组出现 S/A 的概率 | 三组至少一张 S/A |
|---|---|---|---|---|---|---|
| 绿（静默） | 1.09 | 0.89 | 1.38 | **3.37** | 42% | **69%** |
| 蓝（故障） | 1.01 | 0.89 | 1.19 | 3.08 | 42% | 63% |
| 橙（储君） | 1.01 | 0.69 | 1.21 | 2.90 | 33% | 48% |
| 粉（亡灵） | 1.04 | 0.81 | 0.81 | 2.67 | 23% | 45% |

（S/A 档张数：绿 普通 2 / 罕见 3 / 稀有 4；蓝 1 / 3 / 4；橙 1 / 1 / 3；粉 1 / 2 / 2。）

分档整体和人类结果方向一致【统计，全版本】：拿了 S 档牌的局胜率 34.5%、A 档 33.6%、B 档 27.6%、C 档 25.2%、X 档 17.6%（事件局整体 29.3%）。

### 4.2 推荐规则

1. **默认：蓝 ≥ 绿 > 橙 > 粉。**
   - 绿色好牌最多，但其中不少（墨之刃、刀刃之舞、尖啸、萎靡、暴露）要会「算时机 / 认识小刀」，人类数据也偏弱；
   - 蓝色的好牌最「直白」：超临界态（+4 能量）、机器学习（多抽）、超能光束（全体 24）、启动流程（10 格挡）、充电、暴涨（+2 力 +2 敏）、快速检索（抽 3）——**最不依赖战斗规划器认识它们**，社区结果也最好。程序战斗还没为别家牌补知识库之前，蓝色优先。
2. **牌组已经有消耗引擎**（无惧疼痛 / 黑暗之拥 / 灰烬打击 / 燃烧契约 / 重振精神 / 恶魔之焰 中 ≥2 张）→ **橙色提到第一**：暴政（每回合自选烧一张）、轰击（烧掉后每回合免费 18 伤）、护驾（打击变 0 费格挡并自带消耗）、冲锋（打击变 0 费 13 伤）全是消耗线的 S/A。
3. **缺群伤**（群伤牌 < 2 张，第二幕盛碗虫、虫群类普通战、第三幕的要求）→ 蓝（超能光束、扫荡射线）或绿（回响斩击、匕首雨）。
4. **缺格挡**（每回合格挡达不到本幕要求）→ 绿（灵动步法、扫腿、后空翻、余像）。
5. **力量线**（恶魔形态 / 燃烧 / 与我一战！等 ≥2 张）→ 绿（小刀多段吃力量），其次粉（根除）。
6. 粉色一般放最后：好牌集中在罕见组（腐败、致死性），稀有组一半以上要奥斯提 / 灾厄 / 虚无体系；它的「人类强牌」精神过载对程序是陷阱（4.3）。

### 4.3 陷阱（看着强、程序别拿）

## 6. 我们的程序为什么三次都跳过

案例：种子 `TF052CZ0SHL0`（`agent/lab/trace-hk/TF052CZ0SHL0.json` 第 362~365 步；页面 `agent/reports/两局详细记录.html`），第二幕第 14 层（下一步篝火、再下一步 Boss 帝皇蟹），血 48/90，牌组 23 张（格挡偏多、输出不足）。

| 步骤 | 程序看到 | 做了什么 |
|---|---|---|
| 选色 | 橙 / 绿 / 蓝（这次粉色被随机删了） | 选蓝 |
| 普通组 | 编译冲击 / 趁势打击 / 光束射线 | 跳过 |
| 罕见组 | 折射 / 快速检索 / 压缩 | 跳过 |
| 稀有组 | 遗传算法 / 打碎 / 创造性AI | 跳过 |

按本文分档，正确做法是：**罕见组拿快速检索（A）**；普通组拿**趁势打击或光束射线（B，牌组正缺输出、下一场就是帝皇蟹）**；稀有组三张都是 C，跳过。之后这局在帝皇蟹掉了 64 血。

### 6.1 选色：为什么选蓝（这一步没错）

`agent/policy/events.py:58-62` 用 `data/event_stats.json` 的社区胜率打分，样本少的向 30% 收缩（`event_prior_n=30`）：
蓝 (0.458×131+0.3×30)/161 = **0.429**，橙 (0.466×58+9)/88 = 0.409，绿 (0.341×232+9)/262 = 0.336。蓝最高，学到的偏好（`learned_prefs.json` 里 ±0.03）影响很小。结论：选蓝和本文推荐一致。

### 6.2 选牌：一层一层看分数（我按当时状态离线重算了 `rewards.value`）

`agent/policy/rewards.py:50-64`（`pick_mode=model`）：

```python
u = pickmodel.utility(i, card.get('type'), deck, act)
...
elif u is not None:
    s = u - pickmodel.skip_utility(deck, act)
else:
    return P['pick_unknown_value']          # params.json: -0.5
```

| 牌 | 选牌模型认识吗 | 底分 `value()` |
|---|---|---|
| 编译冲击 | 认识 | −1.50 |
| 趁势打击 | 认识 | −1.60 |
| 光束射线 | 认识 | **+0.40** |
| 折射 / 快速检索 / 压缩 / 遗传算法 / 打碎 / 创造性AI | **不认识** | 一律 **−0.5** |
| 跳过 | — | 0（门槛）+ 学到的偏好 `pick:SKIP` 三项合计 **−1.30** |

只看这一层，跳过（−1.30）比每一组最好的牌都低：程序本来会拿光束射线、以及另外两组里「未知牌」中的一张（随机的、不一定是对的那张）。**真正让三组都变成跳过的是下一层：模拟实打。**

### 6.3 模拟实打（simeval）把它们否掉了

`params.json` 里 `simeval_pick: true`，`rewards.py:102-112`：

```python
opts = [(o[0], v / P['simeval_pick_scale'] + P['simeval_prior_w'] * o[1], o[2]) for o, v in zip(opts, sc)]
#             实打分（每少掉 5 血算 1 分）      + 0.5 × 上面的底分
```

要让跳过赢，每张牌的实打结果都得比「不拿」差 5~8 血以上（光束射线要差 7.6 血，未知牌要差 5.3 血）。我用同一状态做了一次只读复现（每副牌 2 个种子，和程序设置一样；程序实际还会以 40% 权重打下一幕的 Boss / 精英，我为省时间只打本幕 Boss + 3 个精英；牌组、遗物按记录还原，升级和药水对不上）：

| 牌组 | 加权平均掉血 | 和原牌组比 |
|---|---|---|
| 原牌组 | 113.2 | — |
| + 折射 | 71.2 | 少掉 42.1 |
| + 快速检索 | 71.0 | 少掉 42.2 |
| + 压缩 | 78.6 | 少掉 34.7 |

两个事实：
1. **「+折射」和「+快速检索」8 场的掉血逐场完全相同** → 这两张牌在模拟里**从来没被打出过**（死牌）。原因见 6.4：战斗规划器不认识它们。
2. 一张从没被打出的死牌，就让结果差了 42 血——**这是洗牌变了（牌组多一张，抽牌顺序全变）带来的噪声**，不是牌的价值。按 `simeval_pick_scale=5` 换算是 8 分，而选牌模型给好牌和坏牌的差距只有 1~2 分。
   这次复现的噪声碰巧偏向「拿」；实战那次（牌组、遗物、药水和我复现的不完全一样）碰巧偏向「跳过」，三组都跳过了。

> 这一点**不只影响这个事件**：只要开着 `simeval_pick`、样本只有 2 个，所有选牌都在被洗牌噪声左右。建议另开一项单独检查（例如：同一副牌只换「新加的那张」时固定其余牌的相对顺序，或把样本加到能让噪声 < 1 分），本文不展开。

### 6.4 根本原因：三处数据都没有别家牌

| 位置 | 问题 |
|---|---|
| `agent/tools/train_pick_model.py:56` | `if 2 <= len(offered) <= 5 and len(picked) <= 1:` —— 色彩哲学家一个地图点有 **9 张候选、最多选 3 张**，整条被丢掉；万花筒（一个点 6 张）也一样。所以选牌模型只认识从棱彩宝石等普通奖励里见过的 70 张别家牌（几乎全是普通牌），罕见 / 稀有基本都不认识（`data/pick_model.json` 的 vocab：静默 21、储君 17、亡灵 16、故障 16 张）。另有 `n >= 15` 的出现次数门槛（第 69 行） |
| `agent/build_knowledge.py:98` | 知识库只收 `ironclad / colorless / curse / status / event / token` 颜色 → `kb/cards.json` 里**没有任何别家牌** → `policy/knowledge.py:18-33` 的段数、群伤、易伤、虚弱、抽牌、能量、能力价值表都查不到 → 战斗规划器只能看懂引擎给的伤害 / 格挡数字，「抽 3」「+4 能量」「给 2 易伤」在它眼里等于什么都没做 |
| `agent/policy/rewards.py:64` | 不认识的牌一律 `pick_unknown_value = -0.5`，不分好坏；`kb.counter_bonus`、`buildrules.card_bonus` 也都靠知识库标签，对别家牌全是 0 |

### 7.3 别家牌的选牌（`policy/rewards.py`）

候选里有别家牌时（这个事件、万花筒、棱彩宝石），**别家牌不走选牌模型、不走实打**，直接查表：

```python
TIER_VALUE = {'S': 2.0, 'A': 1.0, 'B': 0.2, 'C': -0.6, 'X': -3.0}
def other_color_value(card, st, group_rarity):
    t = OTHER_TIER.get(cid(card), 'C')
    v = TIER_VALUE[t]
    if t == 'B' and 补的是牌组缺口(card, st):   v += 0.4     # 缺群伤 / 缺格挡 / 缺易伤 / 缺能量
    if group_rarity == 'Common' and t != 'A':    v -= 0.6     # 普通组只拿 A（3.2 节：拿普通组的局胜率低 12 个点）
    v -= 0.1 * max(0, len(deck) - 25)                         # 牌组越大越挑
    if card.get('upgraded'): v += 0.1
    return v
# 一组 3 张：取 v 最大的；v > 0 才拿，否则跳过。这一步不加 learned_prefs 的 pick:SKIP 偏好（那是对铁甲自己的牌学的）。
```

- 精神过载这类「给自己挂灾厄」的牌，在规划器会算灾厄死线之前留在 C 档。

### 7.5 训练数据（以后重训选牌模型时）

`tools/train_pick_model.py:56` 前面加一步：一个地图点的候选超过 5 张时，**按稀有度（这个事件）或每 3 张一组（万花筒）拆成几个独立的决定**，每组最多 1 张被选。这样模型就能学到别家罕见 / 稀有牌（v0.111 约 1578 个决定，全版本约 8600 个）。

### 7.6 优先级

1. 7.2 + 7.3（小，半小时）：直接解决「白走一个事件」。
2. 7.4（中）：不做的话，拿到的别家牌在战斗里也打不好；做了以后万花筒 / 棱彩宝石也受益。
3. 7.5（顺手，重训时再做）。
4. 6.3 提到的实打噪声（大，影响所有选牌，建议单独立项）。

## 8. 值不值得专门写规则

- **频率**：程序每局约 5.5% 碰到（200 局约 11 次）；加上万花筒 / 棱彩宝石，用同一张表的场合更多。
- **收益**：这个事件是**免费的一次「保证稀有」选牌 + 一次罕见选牌**。按第 4 节，选蓝 / 绿时约 2/3 的概率三组里至少有一张 S/A。白白跳过等于少打一个精英的奖励。
- **成本**：7.2 + 7.3 只要一张表和二三十行规则，不需要调参、不需要跑实验验证机制（机制已由源码确认）。
- **结论**：值得写，但**按「小规则」做**，不要为它单独做实验调参；更大的收益在 7.4（规划器认识别家牌）和 6.3（实打噪声）。

- 数据：`sources/community-runs/ironclad-a10-v0.111.0.jsonl.gz`（9761 局，铁甲、A10、v0.111.0；含 623 局带 BaseLib 模组标记，未剔除，四种颜色里模组局占比 5~9%，差别不大）；补充 `ironclad-a10-all.jsonl.gz`（全版本 70395 局）、`elite-ironclad-a10-v0.111.0.jsonl.gz`（高手 199 局，只用来看选择，不算胜率）。
- 事件识别：`map_point_history` 里 `rooms[].model_id == EVENT.COLORFUL_PHILOSOPHERS`；颜色取 `player_stats[0].event_choices[0].title.key` 的倒数第二段；三组牌按 `cards.json` 的稀有度把 9 张 `card_choices` 分成普通 / 罕见 / 稀有三组（有 6 组出现过一组 6 张的情况，原因没查，量太小，按原样计入）。
- 「同位置基线」：第二幕同一个地图点下标还活着的局的胜率，按事件实际出现位置加权。
- 这些统计脚本是一次性的，放在会话临时目录里，没有放进项目；口径如上，需要时可以照着重写。
